# Business Knowledge（业务知识）

决策背景与业务规则。格式建议：一篇文章回答一个业务问题，开头一段"为什么这事重要"。
新来的同事（人或 agent）读完这一目录，应该能回答"我们为什么做这个产品方向"。

## 我们从解决什么问题出发
**一句话**: 内部合同散落在个人邮箱/共享盘/微信群，找一份合同的当前状态要靠问人；本工作台把合同全生命周期（起草→审核→签署→履行→变更→结算→归档）收敛到一处、可检索、带版本与权限。

**为什么这事重要**：合同是钱与责任的法律载体。状态散乱意味着：
- 到期/里程碑/收付款没有统一提醒 → 该收的钱漏收、该付的钱逾期。
- 生效后谁来改、改成什么都没有留痕 → 追责无据。
- 金额以浮点人算人录 → 错账。

**这个工作台解决的，是"每一份合同当前到底是什么状态、下一动作该谁做"这一个核心问题**。其余（单据模板、审批流、电子签章）都是为守住"状态可追、金额可信、越权被拒"这三个底线服务的增量。

## 我们选择的关键业务取舍（写文档时引用）
1. 生效即冻结：合同主体只读，变更走"变更单"继承版本——法律与审计要求可追溯。
2. 相对方独立成实体——同一个客户反复签合同是常态，去重并复用其收付款/历史。
3. 三档角色（admin/editor/viewer）够用即止：内部工具不做企业级 RBAC，权限只在服务端强校验。
4. 零依赖优先：内部低频工具不为臆想规模上数据库，本地 JSON 可整体迁移。
