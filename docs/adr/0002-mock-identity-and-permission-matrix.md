# ADR-0002: Mock 身份 seam 与权限矩阵（合同 MVP）

日期：待首次 commit 前固定。状态：C2/C3 已批准。
影响面：server 授权、所有 API 测试、前端角色提示。

## 背景
brief 范围仅合同 CRUD＋状态机＋角色，仓库零登录设施（真认证为 non-goal）。角色如何落到请求、以及三档角色各自的写权限边界，需要一次性定死，避免实现时各写各的。

## 决策
1. **身份 = mock 头**：客户端携带 `X-User-Role: admin|editor|viewer` 模拟登录身份，服务端据此强制授权；头缺失或非法取值 → 401（不落入业务分支）。真认证（登录/SSO）上线时替换此 seam，服务端授权点不变。
   - 反直觉点（为何这样而非前端自报身份）：授权**决策**在服务端，按服务端读到的角色判定；头只是"谁在调用"的占位。这是"服务端强校验、不信前端"的落地形式，不是信任前端。
2. **权限矩阵**：

| 动作 | admin | editor | viewer |
|---|---|---|---|
| GET 列表/详情、GET 相对方 | ✔ | ✔ | ✔ |
| 新建合同 | ✔ | ✔ | 403 |
| 编辑（未冻结） | ✔ | ✔ | 403 |
| 迁移 draft→in_review / in_review→draft / pending_sign→active / active→archived | ✔ | ✔ | 403 |
| 审批 in_review→pending_sign | ✔ | 403 | 403 |
| 作废→void / 到期→expired | ✔ | 403 | 403 |
| 删除 / 改相对方种子 | ✔ | 403 | 403 |

3. **相对方**：MVP 以只读静态种子承载（`data/counterparties.json`），合同持 `counterparty_id` 引用；相对方 CRUD 后续。

## 权衡
- 失败影响：mock 头可被伪造，但部署是内部网络 + 后换真认证，可接受（`// ponytail: 认证上线前保持 mock`）。
- 备选：内建登录表 —— 超出 MVP 范围、引入会话状态管理，拒绝。

## 替代方案
- 无 mock、按 IP/离线白名单 —— 不可测、不可扩展，否决。
- 前端上报角色 —— 违背"服务端强校验"，否决。
