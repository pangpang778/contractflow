# 数据规范（Data Standards）

规则的存储形态、字段单位、状态约束。空节合法——沉淀渐进。

## 金额表示
- 所有金额字段整数存储，单位"分"（currency: "CNY"）。禁止浮点。
- 钱就整数: 收付款/预算换算成"分"，展示层再转元。
- 为什么: 浮点误差在合同金额上就是实打实的错账；整数"分"规避 IEEE754。

## 日期与时间
- 存储 ISO 8601 字符串（UTC，形如 `2026-08-30T10:00:00.000Z`）；日期字段用 `YYYY-MM-DD`。
- 展示层按本地时区格式化；前后端不经手 epoch 裸数字当业务日期。
- 为什么: 可排序、可比较、跨时区一致，避免"今天"错位。

## 实体关系
- 相对方（counterparty）与合同（contract）独立；合同持 counterparty_id 引用，不内嵌对方全名。
- 收付款项挂里程碑(id)/合同(id)；里程碑挂合同。
- 为什么: 相对方去重、账户级统计复用，名称变更只改一处。

## 状态机
- 合同生命周期状态见 CONTEXT.md"合同生命周期"，转移白名单先于存储：非法跳转服务端拒绝。
- 生效后主体字段只读；变更走 amendment（持 parent_contract_id）。
- 为什么: 冻结与追溯是合同系统的法律底线，状态先于数据校验。

## ID 约定
- 主键字符串雪花/时间戳型（`c_<epoch>-<rand>` / `cp_<...>` 前缀分域），不依赖自增。
- 原因: 本地 JSON 存储无自增事务，前缀分域便于跨实体检索与排错。
- 补充: 不允许把用户可读名当 ID；ID 生成后不可变。

## 数据规模与迁移
- 单文件 JSON 存储；单文件达到 ~10MB 或并发写入争用出现时，再评估按相对方分片或换数据库。
- 已知上限注释: `// ponytail: 单 JSON 文件，容量到顶再换`。
- 为什么: 内部合同量级（低并发）足以跑很久，不为臆想规模预造设施。
