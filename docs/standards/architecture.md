# 架构规范（Architecture Standards）

规则化、可检查的写；每条带一个"为什么"。空节是合法的——沉淀是渐进的。违反即视为缺陷。

## 模块边界
- server / client / shared 三层切分；shared 只放纯函数与合同领域模型，不透传 http/store。
- 为什么: 领域逻辑单侧依赖，前端不复制业务规则，避免规则漂移。

## 错误处理
- 服务端每个路由兜底异常，返回统一错误信封（ok/data/error）；不向客户端抛栈。
- 金额、状态机跳转、越权三类错误必须显式处理，不得吞掉。
- 为什么: 合同/金额场景静默失败不可接受；统一信封让前端稳定渲染错误态。

## 依赖方向
- client → 只调 server 提供的 JSON API；不直接读写存储文件。
- server → 通过存储接口（Storage）访问本地 JSON；存储实现可替换，不绑定文件系统。
- 为什么: 保持"零依赖、可替换存储"的约束（CLAUDE.md 架构原则），演进不加锁死运行时依赖。

## 副作用与不可变性
- 对合同的写操作返回新对象/新版本，不原地 mutate；生效后的主体字段冻结。
- 为什么: 版本可追溯、并发安全、符合 ADR-0001 的共享环境心智。

## 并发与锁
- 内部工具低并发容忍；写操作为整存整取（read-modify-write）时加进程内单例锁。
- 已知上限注释: `// ponytail: 单例锁，多实例/高并发再换数据库`。
- 为什么: 以最小成本换取金额字段不丢写，不预造分布式设施。
